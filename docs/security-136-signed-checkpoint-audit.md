# SECURITY-136 — Signed checkpoint for offline SQLite restore

**Production: NO-GO.** `security/local/security136-signed-checkpoint.cjs` verifies a domain-separated Ed25519 signature over canonical `version`, `digest` and sorted per-game `heads`. It rejects tampering, unknown/inactive/revoked keys, malformed signatures and invalid checkpoint shapes. `.github/scripts/test-security-136-signed-checkpoint.cjs` builds a disposable SQLite ledger with SECURITY-130's synthetic worker, derives a checkpoint using SECURITY-135, verifies the signed current checkpoint and rejects an older backup against it. The test explicitly proves a **separately signed old checkpoint can still validate an old backup**.

Limitations: test keys are ephemeral, not operationally trusted. There is no independent append-only/latest-checkpoint registry, monotonic externally trusted epoch, protected signing service, trusted timestamp or atomic database/checkpoint update. If both the database and signed checkpoint are rolled back, this implementation cannot detect it. A signed checkpoint is not evidence of current freshness. The SQLite worker uses a synthetic verified flag. No Supabase access, writes, schema changes, production CORE changes, merge or deployment. PR #274 remains Draft.
