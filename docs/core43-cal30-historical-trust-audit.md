# CORE43-CAL-30 — Offline historical prediction trust

## Result

CAL-29 was green in five pull-request workflows on `0805ccdf819a465867f2ee5d1ed1e52cfeb83a49`. CAL-30 adds an offline admission check, a public TSA candidate catalog, and an independent NHL start attestation format. The branch ships with no approved historical policy. The public probes covered a certificate file and did not timestamp an NHL prediction. A historical pilot is blocked pending a compatible second authority, documented operational approval, and independently collected match evidence.

## RFC 3161 audit

| Existing control | CAL-30 finding and treatment |
| --- | --- |
| CAL-16 verifies the signed SHA-256 imprint and request nonce, checks the policy OID and signer fingerprint, and validates the certificate chain at the signed time. | CAL-30 derives the expected certificate, root, and policy from an externally pinned policy. It checks the exact chain and demands disjoint public keys across both chains and the package and observer keys. CAL-16 now exposes both conservative bounds of the signed time interval. |
| CAL-29 compares two declared domain labels and signer fingerprints. | A label or a new certificate does not establish operator or key independence. CAL-30 verifies operator IDs and disjoint public keys against independently approved profiles. Approvers must establish operational separation, clock provenance, and the relying-party scope of each service. |
| CAL-16 checks a caller-supplied normalized start and CAL-29 accepts a supplied UTC cutoff. | CAL-30 verifies a separately signed start attestation bound to the original NHL report bytes, game ID, home and away teams, and scheduled kickoff in the CAL-13 package. The earlier of the signed kickoff and actual-start lower bound is the cutoff. |
| CAL-16 checks certificate validity at the signed time and disallows tokens without an explicit accuracy. | CAL-30 verifies complete signed CRLs at the bounds of that interval and at a policy-pinned review time. The existing accuracy requirement stays in force. The CAL-16 parser relies on OpenSSL text output, so changes in its output can cause rejection and must pass regression and provider testing. |

CAL-30 verifies the signed package and witness through CAL-13 before comparing times. Both independent tokens must follow the recorded witness observation, accounting for uncertainty, and precede the cutoff. The CAL-16 single-token acceptance path predates this check. Its acceptance result cannot serve as a CAL-30 trust decision. [RFC 3161](https://www.rfc-editor.org/rfc/rfc3161.html) · [RFC 5816](https://www.rfc-editor.org/rfc/rfc5816.html)

## Offline interface and provenance

`verifyHistoricalPrediction(evidence, verifierConfig)` takes two separate inputs. Deployments must supply the expected policy SHA-256 through verifier-owned configuration and replace it when approvals, revocation information or keys change. A pin from the submitted archive defeats this trust boundary. The verifier has no embedded approved pin and performs no network or database operations.

- `verifierConfig` holds `policyBytes` and `policySha256`. The compact UTF-8 policy `core43_cal30_policy_v1` pins the mode, whole-second UTC review time, CAL-13 registry digest and root key, NHL observer operator and Ed25519 public key, and exactly two authority profiles. Each profile pins operator ID, approval record digest, expected timestamp policy and max accuracy, certificate fingerprints in leaf-to-root order, and the SHA-256 of each exact PEM CRL in issuer order. The attestor and registry public keys are base64url DER SPKIs.
- `evidence` supplies the original `packageBytes`, `registryBytes`, two timestamp entries keyed by approved authority ID, and `nhlStart`. Each entry carries the original request and response, the exact certificate chain, complete PEM CRLs, and the archived operator approval record. The test builds an example policy and package using only disposable keys.
- `nhlStart` supplies `report`, `statement`, and `signature`. An observer operating independently of the prediction publisher fetches the final NHL Game Summary over HTTPS, archives the original bytes, checks the game and teams, and records the official start converted to UTC. For minute-resolution reports the observer records the beginning of that minute. Ambiguous local dates, offsets, or ambiguous hour interpretations require independent corroboration before signing. The compact UTF-8 statement uses `core43_cal30_nhl_start_v1` and is signed with Ed25519 over the schema name, a NUL separator, and the exact statement bytes. It includes game ID, teams, scheduled kickoff, report URL and digest, actual start, precision and observer time. CAL-30 verifies the attestation and source byte binding offline. It relies on the pinned observer to authenticate and interpret NHL's unsigned HTML. [Official NHL Game Summary example](https://www.nhl.com/scores/htmlreports/20252026/GS020001.HTM)

A missing or rejected item yields `trusted: false`. A successful simulation also yields `trusted: false`. The historical result is valid as of its pinned review time and policy digest. It requires all checks above and can be superseded by new revocation information. CAL-30 neither assigns an outcome to the game nor activates any hosted collection.

## Revocation and CAL-31

CAL-30 uses direct, complete CRLs. OpenSSL validates their signatures and chain coverage using only the pinned root and intermediates. One CRL issued by each chain issuer must cover the entire uncertainty interval and the reference review time. A missing, substituted, stale, future, invalidly signed or revoking list fails closed. The reference review comes after the signed NHL observation. Root approval and removal belong to policy management. The conservative same-CRL interval requirement makes late retrospective cases without sufficient archival coverage ineligible. [RFC 5280 §5–6](https://www.rfc-editor.org/rfc/rfc5280.html) · [OpenSSL verification options](https://docs.openssl.org/master/man1/openssl-verification-options/)

1. Find a second approved operator whose signed token includes explicit accuracy, or independently review the provider's authenticated OID-specific accuracy policy before proposing any verifier change. Confirm service terms, clock and key custody separation, and archival access. Keep both candidates unapproved until these checks are complete.
2. Archive the source CRLs, publish a new independently pinned review policy on rotation or revocation, and define how earlier decisions are re-reviewed after compromise. For a future OCSP profile verify the exact certificate ID, issuer or delegated responder authorization, signature, freshness and response status. Treat unknown, missing or stale responses as failures. [RFC 6960](https://www.rfc-editor.org/rfc/rfc6960.html)
3. Rehearse with two approved TSAs and one independently attested NHL Game Summary. Retain the evidence for offline replay. Before historical metrics consume a result, require the CAL-30 policy ID and review time and enforce the same gate at admission.
