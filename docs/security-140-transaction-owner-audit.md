# SECURITY-140 — Offline signature-gated SQLite transaction owner

**Production: NO-GO.** This is an isolated proof of concept. `security/local/security140-transaction-owner.py` owns both signature verification and SQLite register update in a single Python control flow. It validates canonical SECURITY-136 checkpoint and SECURITY-137 anchor bytes using Ed25519 via OpenSSL `pkeyutl`, verifies scope and checkpoint fingerprint binding, then acquires SQLite `BEGIN IMMEDIATE` and accepts only the next epoch. The untrusted caller is not passed a generic write operation through this module. `.github/scripts/test-security-140-transaction-owner.py` uses ephemeral keys, adversarial mutations and wrong signers, revoked/inactive keys, duplicate and skipped epochs, eight concurrent submissions and crash-before-commit rollback/retry.

**Important limitations:** OpenSSL is a child process for cryptographic verification, although the Python owner controls the entire validation-to-write sequence. The database remains locally accessible to other code and SECURITY-138 exports an unverified update function. Thus this is **not** a protected or enforceable production security boundary, nor does it prevent an attacker with direct database access from bypassing the gate. Key registry, independently pinned latest epoch, durable remote witness, database file permissions, atomic witness publication, operational backup restore and trusted production caller authentication are not provided. Signature verification precedes `BEGIN IMMEDIATE`; concurrent legitimate submissions are serialized at the register and checked for monotonicity, but external key revocation during that interval is not coordinated.

No Supabase access/writes, no production CORE 4.2 or grants changes, no merge/deployment. PR #274 remains Draft.
