# CORE43-CAL-07 signed pregame export

Status **offline prototype and proposed data flow**. The CAL-06 role migration and CAL-04 live job remain blocked. CI signs synthetic fixtures with an ephemeral key and runs the prototype without database, storage, or signing credentials.

## Producer and delivery

A trusted producer outside GitHub Actions would read the approved columns from the five sources and publish a short-lived, signed bundle for each eligible game. Use an existing approved read path only if its privilege and provenance guarantees can be demonstrated. Any new identity, grants, private storage, and producer job require separate review. Keep the signing key and database credentials exclusively on the producer side. A future consumer could read from private object storage with short-lived credentials scoped to get the named objects. The consumer needs only those read credentials and a pinned producer public key. Use a private delivery channel with a 24-hour proposed retention and a five-minute acceptance window. Repository readers can access GitHub workflow artifacts, so do not publish real source bundles or row data as PR artifacts or logs.

The producer should perform one consistent read-only database snapshot per batch. Derive `asOf` when acquiring the snapshot and record `issuedAt` from the trusted producer clock after export preparation. Select rows known at that snapshot and compare original timestamp precision before normalizing for transport. Do not reconstruct an earlier bundle from rows first seen later. Query by the game and participating teams and use explicit projections and deterministic ordering. If limits are exceeded or a source query fails, skip the affected export with a redacted reason. Never send a partial response as a complete bundle.

| Supabase table | Export scope and exact columns |
| --- | --- |
| `nhl_core43_schedule_snapshots` | One game 45–75 minutes before kickoff. Take the latest eligible fetch after verifying schedule evidence agrees on matchup and kickoff. `game_id, away_team, home_team, kickoff_at, fetched_at` |
| `nhl_prediction_archive` | One matching pregame CORE 4.2 baseline. `game_id, away_team, home_team, core42_predicted_at, core42_away, core42_home` |
| `nhl_core43_rotowire_observations` | Pregame observations for this game and both teams. Preserve competing observations for the existing ambiguity checks. `game_id, team_code, goalie_name, observed_status, observed_at, source_snapshot_at` |
| `nhl_core43_goalie_identity_map` | Eligible identity evidence for both teams and the observed goalies. Keep competing identity records visible to the resolver. `goalie_id, goalie_name, team_code, observed_at` |
| `nhl_core43_goalie_snapshots` | Find the latest uniquely eligible `all` source snapshot before restricting goalie rows to the two teams. If that snapshot lacks required coverage, skip the calculation instead of silently substituting an older snapshot. `goalie_id, team_code, situation, fetched_at, created_at, source_sha256, x_goals_against, goals_against, shots_against` |

## Bundle and verification

- The producer emits a single compact UTF-8 JSON object in JavaScript `JSON.stringify` form. Its exact top-level fields are `schema`, `source`, `keyId`, `gameId`, `asOf`, `issuedAt`, and `tables`. Use schema `core43_cal07_pregame_export_v1`, UTC timestamps with milliseconds, decimal string IDs and finite JSON numbers. The five table keys are `schedules`, `predictions`, `observations`, `identities`, and `goalieSnapshotRows`, as listed above. Transport at most 64 KiB and 64 rows per table. Treat size-limit hits as rejected export candidates.
- Send a detached 64-byte Ed25519 signature over the UTF-8 schema identifier, one zero byte, and the exact JSON bytes. Publish both together using an immutable object/version identifier and limit the download size before buffering. The consumer binds `keyId` and `source` to a pinned public key configured independently of the bundle. Use different keys for different environments. Rotate or revoke keys through trusted configuration changes. No trust is placed in a key or URL supplied by the export.
- The consumer verifies the signature before parsing, checks the allowlisted tables and columns, and rejects unexpected fields, duplicate rows, a mismatched game or team, invalid chronology or mixed goalie snapshots. It computes SHA-256 of the verified JSON bytes as the bundle identifier. The upstream `source_sha256` identifies the archived goalie snapshot as reported by the producer. The signature attests to the producer and the exact exported bytes. Verifying the upstream snapshot hash or export completeness separately would require the original source and a reviewed producer.
- The consumer uses a trusted wall clock. It requires `asOf ≤ issuedAt ≤ now`, a maximum age of five minutes from `asOf`, and a kickoff 45–75 minutes away both at snapshot time and evaluation time. Row timestamps are bounded by `asOf`. Reuse the existing archived goalie adapter, pregame assembly and CORE 4.3 planner, including their evidence and ambiguity checks. Missing evidence yields no accepted variants.
- A replay of identical bytes retains the same bundle hash. A reissued or reordered bundle may change the hash, so semantic deduplication uses the existing CAL-03 key for game ID, canonical kickoff instant, the fixed 60-minute window, and coefficient. The same four keys remain duplicates after reissue. An actual kickoff change gets new keys. Future live execution must restore a trusted ledger before processing and serialize conflicting consumers. Check and update that ledger atomically after accepted results, with retries, so concurrent runs and interrupted jobs cannot accept a variant twice. Missing or corrupt history blocks processing. The offline prototype requires prior keys as an explicit argument, with an empty list reserved for fixtures or an intentional first run. It makes no ledger writes.

## Verification and activation boundary

`node --test scripts/test_core43_cal07_export.cjs` exercises the existing planner with synthetic signed rows, verifies all four coefficients, checks retries and rescheduling, and rejects altered data, untrusted signatures, stale or out-of-window exports, unexpected fields, mixed snapshots, and duplicates. The prototype contains no producer, deployment, network delivery adapter, or live workflow wiring. Activation needs a reviewed read path, authenticated private delivery, key rotation, producer completeness tests, and a verified ledger recovery procedure.
